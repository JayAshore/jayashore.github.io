代码评审的目标不是证明作者写得不够漂亮，而是尽早发现会影响用户、数据和维护成本的问题。评审时可以按风险从高到低进行，而不是从格式细节开始。

## 四个优先级

1. **正确性**：边界条件、错误处理、并发行为和数据一致性是否成立？
2. **安全性**：输入是否可信？是否可能泄露敏感信息、越权或执行危险操作？
3. **可维护性**：命名、模块边界和抽象是否帮助下一个人理解代码？
4. **风格**：格式化、命名偏好和小范围重构放在最后讨论。

## 让评审意见更容易被采纳

一条好的意见包含观察、风险和建议。例如不要只写“这里不够健壮”，而是说明：“当接口返回空列表时，这里会访问第一个元素并抛出异常；建议在进入循环前处理空结果，并补一个测试。”这样的评论可以被验证，也不会把讨论变成人身评价。

```ts
function first<T>(items: T[]): T | undefined {
  return items.length > 0 ? items[0] : undefined;
}

function displayName(names: string[]): string {
  return first(names) ?? '暂无名称';
}
```

## 评审前自动化

格式化、类型检查、单元测试和静态扫描适合交给 CI。自动化先过滤机械问题，人工评审就能集中在业务规则、设计取舍和异常场景上。评审完成后，最好把高价值讨论沉淀为测试或文档，让同一个问题不必重复出现。
