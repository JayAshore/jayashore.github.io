# 可复用的Prompt
```txt
第1轮：
先别写代码。
请先把这道题拆成：
- 业务对象
- 状态流
- 核心接口
- 关键边界
- 可能影响得分的部分

第2轮：
基于上面的拆解，先输出一个 spec 和 task。
要求：
- spec 说清楚题目要解决什么
- task 说清楚要做哪些步骤
- 不要直接进入完整实现

第3轮：
现在只做最小可运行骨架。
要求：
- 先保证 baseline 能启动
- 只保留核心目录和入口
- 把每个文件的职责写清楚
- 不要追求完整功能

第4轮：
开始补主流程。
要求：
- 只做正常路径
- 不要先扩边界
- 如果有状态迁移，请明确写出允许的转移关系
- 每次只改一个问题点

第5轮：
开始补边界。
请按场景逐个处理：
- 重复提交
- 幂等处理
- 状态回退
- 异常重试
- 部分成功后的兜底
每个场景先说处理方案，再改代码。

第6轮：
根据我现在的报错、样例反馈或运行结果，先定位问题，不要大改。
如果是状态机问题，只改状态迁移；
如果是接口问题，只改接口返回；
如果是测试问题，只补测试；
如果是实现问题，只改对应模块。

第7轮：
帮我做一次定点优化。
请基于当前代码和反馈，只提出最小修改方案，并说明：
- 改了哪里
- 解决了什么
- 还剩什么没验证
```


# 做题方法补充
1. 先看README和测试用例，别上来就写。
2. 时间不够时，先拿能拿的分，再补完整性。
3. 每轮只改一个核心点，方便判断涨分来自哪里。
4. 用 search/replace做精确修改，少做整段重写。
5. 每次跑完都保存一个可回退的时间线节点。
6. 把模型的输出当草稿，把报错和样例反馈当真凭据。
7. 卡住时先缩小问题，不要一口气推翻整份代码。
8. 复制代码主体后，让模型围着具体反馈反复优化，比空谈“继续优化”有效得多。
